# Nanobot 个人 IM 连接

入口：银行 AI →「连接微信、QQ 或企业微信」，或 `/channels`。
每个登录账户分别管理自己的机器人，不依赖平台统一 Bot Secret。

## 用户流程

- 微信：输入银行密码并确认授权 → 获取微信 iLink 二维码 → 微信扫码确认 →
  在机器人私聊发送银行页面的配对码。
- QQ：在 QQ 开放平台创建机器人，复制 AppID/AppSecret，测试 QQ 加入沙箱成员 →
  在银行页面填写配置、确认授权 → 给机器人私聊发送配对码。
- 企业微信：创建智能机器人，选择 API / 长连接模式，复制 Bot ID/Secret →
  在银行页面填写配置、确认授权 → 给机器人私聊发送配对码。
- 配对码有效十分钟，每码最多二十次尝试；它不是银行密码，只有银行页面显示明文。
- 配对后发「查一下余额」。资金操作仍需打开银行 APP 的真实单据授权。

平台可能限制账号资格、机器人发布、测试成员或可见范围。扫码不保证微信侧放行。
QQ 不支持在这里扫个人 QQ 登录码；企业微信群 Webhook 也不是此入口所需凭据。

## 实际复用和架构

```text
银行 /channels ─ 登录 + 密码复核 ─ 银行配置 API
                                      │ 按当前客户解析连接 UUID
                                      ▼
                              私有 Python supervisor
                                      │
                 ┌────────────────────┼─────────────────┐
                 ▼                    ▼                 ▼
           用户甲 QQ 进程       用户乙微信进程       用户丙企微进程
                 └────────────────────┬─────────────────┘
                           Nanobot 原生渠道 / MessageBus
                                      │ 已验明的私聊身份
                                      ▼
                          银行内部 IM API / 幂等运行
                                      │
                          真实 Nanobot + 模型 + 银行 MCP
```

固定发布包 `nanobot-ai==0.3.0`，没有 fork 或编辑依赖源码：

- `ChannelManager`：渠道加载、收发、重连和运行状态。
- `WeixinConnectStore`：真实二维码创建、轮询、取消、过期、保存登录状态。
- `validate_channel_config`：上游字段检查。QQ/企微返回 configured **不表示已经登录或收发成功**。
- 三个原生渠道插件与 manifest 声明依赖；可选依赖在镜像构建时安装，远端用户无安装权限。
- UI 复用上游的凭据配置/扫码交互模式和后端能力，样式由 BankPilot 自己实现；
  未把整个 Nanobot 管理 WebUI、模型设置或通用工具配置开放给用户。

薄适配代码位于 `channel_worker.py` 和 `channel_service.py`。额外的实例级入口钩子
只拒绝群聊和附件，发生在原生下载逻辑之前；不重写平台协议或推理循环。升级版本必须
重新检查这些接口。Nanobot 原生全局配置放在每连接独立的临时目录，不跨用户共享。

## 安全、持久化和状态

- `/api/nanobot/channels` 只接受银行 Session；写操作必须同源。连接 UUID 必须属于
  当前客户，浏览器不能传 customerId、模型配置、任意 URL 或运行目录。
- 配置需要银行密码与明确授权。模型由平台配置，用户不需要提交模型 Key。
- `nanobot_channels` 保存归属、启停、HMAC 身份摘要、一次性配对摘要和最近消息时间。
  QQ/企微同一个机器人不能同时被不同银行用户登记。
- 密钥与微信状态使用 AES-GCM 保存到 Nanobot 数据卷，每条密文绑定连接 UUID，
  文件权限 0600。加密密钥由服务令牌经过专用域分离派生；**轮换服务令牌前必须迁移
  加密状态，否则需要重新连接所有 IM**。数据库、数据卷和服务令牌应一起安全备份。
- 子进程只通过 stdin 得到自己的渠道配置，没有数据库、模型、银行令牌或回调密钥。
  原生插件所需明文配置仅存在受限临时目录；生产环境 `/tmp` 为内存文件系统。
- 插件的 `allowFrom:["*"]` 只允许消息到达可信配对网关，不直接授权模型。银行内部
  API 对连接、私聊发送者与会话做强制核验；未配对身份、另一发送者、群聊都不能查账。
- 同一平台消息 ID 映射同一银行运行，避免重复工具调用。模型每次使用四分钟令牌，
  保留已有银行权限控制、审计、限额和确认机制。
- 解除连接先在数据库撤销权限、在途运行及令牌，再停进程并删除凭据；后台不可达时
  银行访问仍立即阻断，恢复通信后再停止/清理。
- supervisor 每三十秒向银行核验启用连接，进程崩溃后恢复，服务重启后解密自己的
  配置恢复连接；微信状态定期加密快照。网页关闭不停止后台渠道。
- 页面分别显示「后台运行」「等待配对」「身份已绑定」「最近收到消息」，不把配置
  保存当作已连通。SDK 断线/微信登录过期也有对应状态。

## 部署

先备份数据库，再执行 `008_nanobot_channels.sql`；已有 001–005、007 必须已应用。
重建 app 和 nanobot 镜像；没有新增公网端口，不需要额外机器人环境变量。

```sh
docker compose --env-file deploy/.env.production -f deploy/compose.production.yml \
  --profile nanobot up -d --build app nanobot
```

默认最多六条常驻渠道进程，仍受 nanobot 容器 768 MiB / 1 CPU 上限约束；
`NANOBOT_MAX_CHANNELS` 可在服务环境调整，但须先做容量测试。模型运行上限仍是全局两次、
每客户同时一次、每天五十次。回滚到旧镜像可停止新渠道；保留数据库迁移和加密状态。

## 测试与诚实边界

- `test_channels.py`：加密/篡改/密文换租户、路径防穿越、群聊/附件过滤、真实上游
  QR 状态机（网络桩）、两个真实独立配置子进程。
- `nanobot-channels.integration.test.ts`：独立 PostgreSQL 的跨用户访问、过期配对、
  错误配对熔断、身份隔离、消息幂等、撤销授权。
- `evaluate_channels.py`：只允许本地测试，模拟 IM 投递，但运行真实模型和 MCP；
  检查银行审计、回复、消息去重、跨租户不可见、断开后拒绝访问。
- 手机 UI 用真实本地银行 API 验证，不用前端 mock 伪造连接状态。
- 2026-09-06 验证：独立 PostgreSQL 下 38 项银行测试通过；上游 QR 与渠道
  边界测试通过；真实 DeepSeek + MCP 的 APP 回归、模拟 IM 投递回归通过。
  手机 390×844 页面已从真实微信服务取回二维码并轮询状态，随后取消测试扫码。
- **真人微信扫码与 QQ/企微实际私聊收发必须由各渠道账号所有者完成；上述测试不
  等于已经替用户完成了平台登录。**
- 当前是文字私聊，不是群聊、语音和文件处理。没有后台定时付款。
- 进程不是独立容器，使用同一 UID，不能防御依赖任意代码执行或宿主入侵。
  尚未完成生产级多租户安全审计、压力测试、独立租户资源配额和密钥轮换工具。
- IM 出站采用 Nanobot 原生发送，银行侧幂等避免重复操作，但没有跨服务事务性
  出站消息队列。进程在结果投递时崩溃可能漏回复，银行 APP 保留运行和真实单据。
