# 安全设计与自评报告

## 权限分级

| 级别 | 当前动作 | 技术控制 |
|---|---|---|
| GREEN | 余额、流水、账单分析、订阅识别 | 只读白名单工具；确认意图后自动执行 |
| YELLOW | 日累计不超过 1,000 元的转账、锁卡 | 服务端生成不可编辑操作凭证；用户明确点击确认 |
| RED | 日累计超过 1,000 元的转账、不受信收款人/设备 | OTP 强验证；授权绑定交易指纹；10 分钟过期；3 次失败熔断 |

风险只能升级不能降级。前端传来的风险级别不被信任，Policy Engine 根据数据库证据重新计算。

## 核心防线

### 幻觉防护

- Agent 只描述 Bank Core 已返回的数据；
- 草稿、等待授权、执行中和成功使用不同状态；
- 只有事务提交后才生成账本编号；
- API 失败统一表述为“未执行/未确认”，不猜测结果；
- 账户、收款人、卡等实体必须在数据库中解析成功。
- 模型未配置、超时、返回非 JSON 或不符合 Schema 时直接拒绝，不使用规则/模板假装成功；

### Prompt 注入防御

- Prompt 永远不能修改权限规则；
- 模型层不持有数据库凭据或写操作工具；
- 工具名、输入结构、金额范围和资源归属在服务端校验；
- 银行流水、商户名等外部文本视为不可信数据，不作为系统指令；
- 生产版需增加输入/输出分类器、Unicode 归一化、间接注入检测和策略回归集。

### 认证与授权

- 红色操作 OTP 哈希存储；
- `authorization_fingerprint` 绑定 operationId、付款账户、收款人、金额和币种；
- OTP 有过期时间、尝试次数和状态；
- 连续 3 次失败锁定 challenge；
- 生产环境应替换为银行现有 SCA，包括 Passkey、人脸、短信、U 盾或硬件签名。

### 交易与账本

- Prepare / Commit 两阶段；
- 操作 ID 与幂等键唯一；
- PostgreSQL 事务与行锁；
- 双分录总和必须为 0；
- 余额 CHECK 约束；
- 重复提交成功操作只返回原凭证，不重复扣款。

### 审计

记录用户原话、意图、风险等级、DAG、每个工具节点、策略匹配规则、授权结果、操作编号、授权指纹和账本编号。演示环境使用关系表；生产环境建议同步到不可篡改/WORM 存储，并对安全事件实时告警。

### 沙箱

当前 Agent 不执行模型生成代码，工具层只有预编译服务端函数，因此不存在任意代码执行路径。若未来开放代码型分析工具，必须放入无网络、只读文件系统、限 CPU/内存/时长的独立沙箱，不可继承银行核心凭据。

## 已知风险与后续项

| 风险 | 当前状态 | 上线前措施 |
|---|---|---|
| 演示 OTP 固定为 123456 | 仅本地演示 | 接入真实 OTP/HSM，密钥轮换 |
| 模型理解和回复仍可能产生偏差 | Schema、实体二次解析、低置信度澄清 | 建立红队与事实一致性评测集，增加输出声明校验 |
| 审计表可由数据库管理员修改 | 原型限制 | WORM/签名日志/独立审计域 |
| 单用户演示，无完整登录 | 原型限制 | OIDC/Passkey、设备绑定、会话风控 |
| 未接 AML/制裁名单/反欺诈平台 | 未实现 | 执行前同步评分与名单筛查 |
| Service Worker 只缓存应用壳 | 有意限制 | 敏感 API `no-store`，完善版本与撤销策略 |
| 卡片锁定无解锁强验证流程 | 部分实现 | 增加解锁红色流程与客服接管 |
| 订阅取消仅展示识别结果 | 部分实现 | 接入代扣平台并走黄色确认 |

## 自评结论

项目已满足赛题最关键的绿色/黄色/红色分级、幻觉防护、操作审计、验证失败熔断和受限工具调用，并以真实事务与双分录证明写操作闭环。它仍是比赛级模拟银行，不具备未经银行集成即可生产上线的条件；上述边界会在答辩中明确说明。
